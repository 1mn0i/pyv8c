# 案例组织、持续推进与外部边界

## 选择案例

用户给出网站时围绕该网站定义目标，不擅自改成探针页后宣布完成。没有指定网站时，选择用户项目已有案例或本地应用，优先明确资源依赖和可重复的初始化/交互。

公开网站、文档应用、组件示例、含 frame/Worker 的页面都能暴露框架问题；不必以风控/挑战页作为唯一测试来源。真实访问低频、有界，只执行任务需要的操作，不默认提交表单、付款、发送消息或修改第三方数据。

同一站点响应可能受出口、Cookie、时间、权限和版本影响。先保存响应摘要，解释两侧内容是否可比；登录或人工验证状态不得擅自从另一个会话复制来证明框架正常。

## 一份案例报告

使用用户指定位置，或项目已有的诊断目录。源代码、测试和案例报告相互链接，原始日志另存，不强制新增 examples README 或仓库级流水台账。

建议结构：

```markdown
# 案例：页面与加载目标

## 条件及结果
版本/源码/二进制/IDL/profile 摘要；访问条件；目标是否达到。

## 已确认差异
现象和阶段 → 两侧证据路径 → 最早分歧和消费者 → 本地复现
→ 根因和修复位置 → 回归结果 → 原站复测结果。

## 剩余问题
分类、影响、证据、已排除解释、下一条可执行调查。

## 环境与工具限制
未观测项、配置/版本差异、外部阻塞及未验证能力。
```

同一结论就地更新，撤回错误判断并给出反证。不要累积“第 N 轮做了什么”的流水记录。

## 什么时候继续，什么时候报告阻塞

- 本地修复通过但网站仍未达标：检查加载时间线新出现的第一处分歧，继续。
- 有待实现能力：明确数据模型和所需 API，按任务范围实现并测试，不能只补接口形状或空对象。
- Chrome 同样失败：检查响应/网络/操作条件，不将它当作两侧行为正确的证明。
- 登录、人工验证、服务器限流/拒绝、设备权限或不可用工具阻止验证：保存依据，减少重试，完成独立可做的框架工作后说明边界。
- 修改引入新失败：先修回归，不以另一站点能加载抵消它。

最后明确区分“目标达到”“框架差异已修但外部验证受阻”“仍有未解决框架差异”。skill 的目标是逐步完善浏览器能力，不承诺任意网站都能加载，也不把一次站点通过当作 Chrome 完整兼容证明。
