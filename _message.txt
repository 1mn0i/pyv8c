feat: give frames their own document, and build the tree the way a parser does

Two threads of work, both measured against Chrome 153.0.8010.52 rather than
assumed: the shape of a parsed document, and what an iframe is.

Parsing.  A document parse now builds html/head/body as it reads, with the
insertion modes a browser uses, so a node lands where its markup puts it: a div
written between head and body ends up in the body, text before head is pulled
into it, and a fragment's nodes go to their innermost element.  Nothing is
re-parented after the parse ends, because re-inserting a parsed subtree moves
it, and moving it disturbs the scripts inside -- a real page guarded by a WAF
lost its challenge cookie that way.  _ensure_skeleton now only fills in what
the parse left out, and never moves a node the parse already placed.

Frames.  HTMLIFrameElement moved to pyv8c/web/dom/html_iframe.py, and its
behaviour is Chrome's, item for item:

- A detached frame hands out no window.  The insertion creates the browsing
  context in the same turn, so i.contentWindow goes from null to a window while
  the script that inserted it is still running.  A realm is normally built on
  its own thread, which waits on the lock a running script already holds; a
  realm asked for from inside a script is therefore built on the calling thread.
- The reflected attributes are Chrome's -- srcdoc, name, sandbox, allow,
  allowFullscreen, width, height, referrerPolicy, loading, contentDocument and
  contentWindow -- including what a missing or unrecognised value reads back as
  (loading is "auto", an unknown referrerPolicy is ""), plus getSVGDocument.
- srcdoc is the frame's own document: about:srcdoc, same-origin with the page
  that wrote it, nothing fetched, and it wins over src.  about:srcdoc inherits
  its creator's origin now, the way about:blank does.
- sandbox without allow-same-origin gives the frame an opaque origin that
  survives navigation: contentDocument is null and reading contentWindow.name
  throws SecurityError.  Without allow-scripts the frame's scripts do not run
  at all -- parser, dynamic, external, inline handler -- and their fetch is not
  made either, while the script elements stay in the document.
- A frame's name is its browsing context name, so window.name, window.frames
  and window.length report it.

Also here, each item found missing or wrong while comparing:

- Document.referrer, compatMode, contentType, dir, and styleSheets with the
  StyleSheetList behind it
- window.name; navigator.cookieEnabled and pdfViewerEnabled; screen.orientation
  and ScreenOrientation
- crypto.randomUUID as a method, which is where Chrome puts it
- PerformanceTiming and PerformanceNavigation; canvas TextMetrics, so
  measureText answers an object; TextTrackList, TimeRanges, canPlayType, play,
  pause and load on the media elements
- History.state reads null rather than undefined, and a window's load event is
  dispatched at the window with the document as its target

Tests: the repro corpus grew to 232 cases -- 225 compared against Chrome and 7
accounted for with a measured reason.  The suite is 852 passed, 7 skipped, with
the interface extractor failing for the environment reason it always had.  The
startup gate is inside its recorded budget: 172.3 ms median against 175.6 ms.

Still open: sandbox grants origin and scripts only so far; allow-popups,
allow-forms and allow-top-navigation are not enforced.
